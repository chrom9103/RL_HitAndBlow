# Hit & Blow

4 つの数字を、CPU より少ない回数で当てる数当てゲームです。ブラウザだけで動きます(サーバー不要)。
CPU は DQN(Deep Q-Network)で学習させたエージェントで、学習の進み具合が異なる 3 つのチェックポイントを
Easy / Normal / Hard として使っています。

## 遊び方

- 秘密の数字は 0〜9 のうち重複しない 4 つの数字です。1 ゲームごとにランダムに決まり、プレイヤーと CPU で共通です。
- 交互に予想します(先攻はプレイヤー)。判定は **Hit**(数字も位置も一致・点で表示)と **Blow**(数字は含まれるが位置が違う・輪で表示)。
- 当てるまでの回数が少ない方の勝ち。同じ回数なら引き分け。プレイヤーが n 回目で当てても、CPU の n 回目まで進めてから確定します。
- 上限は 1 人 10 回。片方だけ未達ならその側の負け、双方未達なら引き分けです。
- CPU の予想した数字はゲーム終了まで伏せられ、判定だけが見えます。結果画面ですべて公開されます。
- 「ヒント」を押すと、残りの候補数とミニマックス法によるおすすめの予想が表示されます(勝敗には影響しません。使った回数は結果画面に表示されます)。

## 起動

Node.js 20.19 以上(22 以上推奨)が必要です。

```sh
cd app
npm install
npm run dev        # 開発サーバー http://localhost:5173
npm test           # ゲームロジックと、学習側との推論一致テスト
npm run build      # dist/ に静的ファイルを出力(任意の静的ホスティングに置けます)
npm run preview    # ビルド結果の確認
```

## CPU の仕組み

### 環境

- 1 エピソード = 1 つの秘密の数字を当てるまで(上限 10 手)。
- 報酬: 1 手ごとに −1。当てたら `11 − 手数` を加算(早いほど大きい)。10 手で当てられなければ −5。
  1 手目で当てれば合計 +9、10 手目なら −9、未達なら −15 となり、少ない回数ほど高くなります。割引率 γ = 1。

### 状態と行動の特徴量

状態は「これまでの予想と判定に矛盾しない秘密の数字の候補集合 C」から作ります。

| 種類 | 次元 | 内容 |
|---|---|---|
| 状態 | 1 | log2 \|C\| / log2 5040 |
| 状態 | 1 | 手数 / 10 |
| 状態 | 1 | \|C\| = 1 か |
| 状態 | 40 | 桁 × 数字ごとの、候補内での出現割合 |
| 行動(予想 g ごと) | 1 | g が候補に含まれるか |
| 行動 | 1 | g で即正解する確率(含まれれば 1/\|C\|) |
| 行動 | 1 | 期待残り候補率 Σ n_r² / \|C\|²(n_r は判定 r ごとの候補数) |
| 行動 | 1 | 判定分布のエントロピー / log2 14 |
| 行動 | 1 | 最大バケット率 max n_r / \|C\| |
| 行動 | 1 | 起こりうる判定の種類数 / 14 |
| 行動 | 1 | g の各桁の出現割合の平均 |
| 行動 | 1 | 期待 log 残り候補数 Σ (n_r/\|C\|) log2 n_r / log2 5040 |

### ネットワークの方式の比較

行動(次の予想)は 5,040 通りあります。次の 2 方式を比べました。

| | A: 全 5,040 通りの出力を持つネット | B: 状態+予想の特徴から価値を 1 つ出すネット(採用) |
|---|---|---|
| 構成 | 43 → 64 → 64 → 5040 | 51 → 64 → 64 → 1 を全予想に適用して最大を選ぶ |
| パラメータ数 | 約 33.6 万(最終層だけで約 32.8 万) | 7,553 |
| 重みのサイズ(float32) | 約 1.3 MB / 難易度、3 つで約 3.9 MB | 約 30 KB / 難易度、3 つで約 90 KB |
| 学習の安定性 | 各出力は自分が選ばれたときしか更新されず、5,040 個の値をばらばらに学ぶ必要がある。「数字の並べ替え」という対称性も自分で見つけなければならず、データ効率が悪い | 予想の性質(候補に含まれるか、候補をどれだけ絞れるか)を通じて予想どうしで汎化するため、少ないデータで安定して学べる |
| 推論コスト | 1 回の順伝播 | 5,040 行の順伝播(状態部分は共通化。ブラウザで 1 手 数十〜百数十 ms) |

重みのサイズ(目安 2 MB 以下)と学習の安定性の両方で B が有利なため、B を採用しました。
B は重みが十分小さいので、量子化(float16 / int8)はせず float32 のまま配布しています(推論一致の確認も単純になります)。

### DQN

- **経験再生バッファ**: 容量 50,000 遷移、バッチ 64 を一様サンプリング。
- **ターゲットネットワーク**: 1,000 更新ごとにオンラインネットの重みをコピー。
- **ε-greedy**: 最初の 300 エピソードは ε = 1(完全にランダム)を保ち、その後 10,000 エピソードかけて 0.05 まで線形に下げる。
- **Double DQN**: 次状態の行動はオンラインネットで選び、ターゲットネットで評価。
  次状態の 5,040 予想すべての特徴をバッファに保存すると大きすぎるため、遷移時点のオンライン Q 上位 32 個の予想の特徴だけを保存して最大化を近似しています。
- 損失は Huber、最適化は Adam、勾配のノルムを 10 でクリップ。
- すでに予想した数字は選びません。最大 Q との差が 1e-9 以内の予想は同点とみなし、アプリでは同点の中からランダムに選びます(学習側の参照実装とテストでは最小のインデックス)。

### 推論と配布形式

- 重みは `app/public/weights/{easy,normal,hard}.bin`(float32 リトルエンディアン、層ごとに W(出力×入力)→ b の順)と `manifest.json`(層の大きさ)。
- ブラウザでは TypeScript で特徴量と MLP の順伝播を実装しています(依存の追加なし)。onnxruntime-web や TensorFlow.js は数 MB の追加になり、この大きさのネットには過剰なため使っていません。
- 計算は Web Worker で行い、画面の操作を止めません。CPU の手番は 0.6〜1.2 秒の間を置いてから表示します。
- **一致テスト**: `training/export.py` が Python の参照推論(`hitblow/policy.py`、float32 の重みを float64 で計算)の結果を
  `app/src/cpu/__fixtures__/parity.json` に書き出し、`app/src/cpu/parity.test.ts` が同じ局面で TypeScript の推論を行って、
  特徴量(誤差 1e-12 以内)・Q 値(1e-9 以内)・選ばれる予想(完全一致)を確認します。

## 難易度の仕組み

1 回の学習ラン(シード 0、30,000 エピソード)の途中経過から 3 つのチェックポイントを選び、難易度に割り当てています(`training/difficulties.json`)。

| 難易度 | チェックポイント | 学習の段階 |
|---|---|---|
| Easy | 600 エピソード | 「これまでの判定と矛盾しない予想が良い」ことを覚えかけた段階。矛盾した予想をよく打つ |
| Normal | 1,300 エピソード | ほぼ矛盾しない予想を打つが、候補を効率よく絞る予想はまだ選べない |
| Hard | 30,000 エピソード | 候補をよく分割する予想を選ぶ。7 回以内に必ず当てている |

### 差を出すための調整

- 最初の試行(学習率 3e-4 で一定)では、1,000〜2,000 エピソードで平均約 5.25 回に達してその後は横ばいになり、Normal と Hard の差がほとんど出ませんでした。
  学習率や更新頻度を一律に下げても、学習曲線が後ろにずれるだけで形は変わりませんでした。
- そこで、**最初の 600 エピソードは学習率 3e-4 で基本を素早く覚え、その後 3e-5 に下げる**スケジュールにしました。
  ε は最初の 300 エピソードは 1(完全ランダム)を保ち、その後 10,000 エピソードかけて 0.05 まで下げます。
  学習率を下げた後はゆっくり上達するため、数百・数千・数万エピソードの各時点で強さに段階的な差が出ます。
- 学習の途中(数百〜千数百エピソード)は強さの変化が急で、隣り合うチェックポイントでも平均回数が大きく揺れます(例: 1,300 エピソードで 5.93 回、1,350 エピソードで 6.90 回)。
  そのため序盤は 50 エピソードごとにチェックポイントを保存し、`evaluate.py --scan` で計測したうえで、狙いの強さのものを選んでいます。

## 難易度 Max(最適戦略)

学習ではなく、**平均回数を最小にする戦略をゲーム木の全探索で厳密に求めたもの**です。
選択画面にはまだ出していません(コード上は `Difficulty` の `'max'` で使えます)。

DQN(Hard)もミニマックス法も、使っている情報は「次の 1 手で候補がどう分かれるか」だけなので、
理論値(約 5.21 回)には届きません。2 手以上先まで読んで初めて分かる差を拾うため、全探索しています。

### 求め方(`training/hitblow/optimal.py`)

候補集合 S をすべて当てきるまでの総手数の最小値を f(S) とすると、f(S) = min_g ( |S| + Σ_{判定 r ≠ 4H} f(S_r) ) です。
平均回数の最小値は f(全 5,040 通り) / 5,040 になります。これを次の工夫で計算しています。

- **分枝限定法**: 外れの判定は 13 種類しかないので、n 個の候補を当てきる総手数には下界があります
  (深さ d で当たるのは最大 13^(d-1) 個)。予想を下界の小さい順に調べ、暫定の最良に届かないと分かった時点で打ち切ります。
  部分問題にも「これ未満なら正確な値が欲しい」という上限を渡します。
- **対称性**: これまでの予想をすべて動かさない「桁の並べ替え × 数字の付け替え」で移り合う予想は総手数が同じなので、代表だけを調べます。
  1 手目はすべて同じなので 0123 に固定し、2 手目は 230 通りまで減ります。
- **メモ化**: f(S) は S だけで決まるので、結果を S のハッシュで保存します。
- **並列化**: 1 手読み(二乗和が最小の予想)の総手数を上限にして、2 手目の候補を複数プロセスで同時に解きます。
  上限未満で解けた 2 手目は、そのプロセスのメモに最善手まで残っているので、その場で決定木にして返します。
- 小さい局面では、対称性も枝刈りも使わない総当たりと結果が一致することをテストで確認しています(`tests/test_optimal.py`)。

### 結果

| 回数 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 以上 |
|---|---|---|---|---|---|---|---|---|
| 件数 | 1 | 7 | 65 | 723 | 2,384 | 1,768 | 92 | 0 |

- 秘密の数字 5,040 通りすべてで、平均 **5.2131 回**(26,274 / 5,040)・最悪 7 回です。
- Ryzen 9 9900X・14 プロセスで、探索に約 54 分かかりました。
  (このときは決定木を別のプロセスで組み立て直したため、さらに約 20 分かかりました。現在は上記のとおり探索中に組み立てます。)

### アプリでの使い方

- 最適戦略は「これまでの判定 → 次の予想」の決定木として `app/public/weights/max.bin` に書き出しています(5,115 ノード、約 30 KB)。
  形式は、ノードを前順に並べた 1 ノード 6 バイト(uint16 予想のインデックス、uint32 子を持つ判定のビットマスク)です。
- ブラウザでは木をたどるだけなので、計算はほぼかかりません(`app/src/cpu/tree.ts`)。
- 毎回 0123 から始まって予想が読まれないよう、対戦ごとに「桁の並べ替え × 数字の付け替え」をランダムに 1 つ選んで、木の予想に掛けています。
  秘密の数字は一様にランダムで、判定は両方に同じ付け替えを掛けても変わらないので、平均回数は変わりません。
- `app/src/cpu/tree.test.ts` で、5,040 通りすべてを打たせた総手数が最適値と一致すること(付け替えありでも同じこと)を確認しています。

## ヒント(ミニマックス法)

ヒントは CPU とは別の、学習を使わない決定的なアルゴリズムです(`app/src/hint/minimax.ts`)。

1. 0〜9 から重複なしの 4 桁、全 5,040 通りを列挙する。
2. 各候補について「これが正解なら、これまでの予想にどんな判定が返るか」を計算し、実際の判定と一致しない候補を捨てる。
3. 考えられるすべての予想(候補以外も含む 5,040 通り)について、返ってくる判定(0H0B、1H2B など)ごとに候補を分け、
   **一番大きいグループが最小になる予想**を選ぶ。最悪の場合でも残りが少なくなるので、ミニマックス法と呼ばれる。
   - 同じ水準なら、候補に含まれる予想を優先する(当たる可能性が残るため)。
   - それでも同じなら、グループの大きさの二乗和(期待残り候補数に比例)が小さい予想、最後は辞書順で先の予想。

1 手目はどの予想も同じ分かれ方(最大 1,440 通り)になるので、計算せず 0123 を選びます。
計算は Web Worker で行い、1 手あたり数十〜百 ms 程度です。

### 全数での結果

秘密の数字 5,040 通りすべてについて、ヒントどおりに予想した場合の回数です(`app/src/hint/minimax.test.ts` で計測・確認)。

| 回数 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 以上 |
|---|---|---|---|---|---|---|---|---|
| 件数 | 1 | 3 | 44 | 558 | 2,218 | 2,043 | 173 | 0 |

- **最悪 7 回**で必ず当たります。7 回はこのゲームで最悪手数を抑える場合の最善です。
- 平均は **5.343 回**(26,930 / 5,040)。三つ目の基準(二乗和)を入れない場合は 5.385 回でした。
- 平均回数そのものを最小にする戦略(約 5.21 回)は、数手先まで読む探索が必要で、このヒントの対象外です。
  ミニマックス法は「最悪の場合」を抑える方法なので、平均では Hard の CPU の方がわずかに少なくなっています
  (難易度と同じ 1,000 ゲームの計測で 5.26 回 対 5.33 回。対戦すると Hard から見て 勝ち 23.7% / 引き分け 57.3% / 負け 19.0%)。
  一方で、最悪 7 回の保証はミニマックス法にしかありません。
  ヒントどおりに打つと、Hard とはほぼ互角で、わずかに負け越す程度の強さです。

## 学習のやり直し方

Python 3.12 で確認しています。学習は CPU で行います(GPU 不要。シード固定・単一スレッド・決定的アルゴリズムで再現性を確保)。

```sh
cd training
python -m venv .venv
.venv/Scripts/activate            # macOS / Linux: source .venv/bin/activate
pip install -r requirements.txt   # PyTorch は CPU 版で十分です(pip install torch --index-url https://download.pytorch.org/whl/cpu)
pytest                            # 判定・特徴量・環境のテスト

python train.py                   # 既定の設定で学習(runs/main にチェックポイントを保存)
python evaluate.py --scan runs/main --games 200   # 全チェックポイントの強さを走査(割り当ての検討用)
```
